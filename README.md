# Predicting lost-time mine injuries from MSHA open data

Module 6COSC017C Machine Learning and Data Analytics, Coursework 1, student ID 13130. The business question: when a mine operator files an injury on US Form 7000-1, can the case be flagged as a likely lost-time injury at once, so that the insurer or self-insured operator opens the reserve, the return-to-work plan and medical case management earlier? The data are three open files from the US Mine Safety and Health Administration (MSHA), joined into one table of 101,609 injured persons from 2010 to 2025, of whom 48.6 % had a lost-time outcome. The final model is a histogram gradient boosting classifier (`hist_gb`), ranked first by cross-validated PR-AUC. On the 20,320 held-out rows it reaches ROC-AUC 0.843 and PR-AUC 0.841 (`reports/metrics/comparison.csv`). At the operating point, a threshold of 0.210 chosen on out-of-fold probabilities for specificity 0.40, recall is 0.943 and specificity is 0.403 (`reports/metrics/comparison_operating_point.csv`). The lookup baseline, the lost-time rate of each nature of injury x body part x sector cell on the training rows, reaches ROC-AUC 0.804.

## Data

Three files from MSHA Open Government Data (https://arlweb.msha.gov/OpenGovernmentData/OGIMSHA.asp):

| File | Rows x columns | One row is |
|---|---|---|
| `Accidents.zip` | 275,220 x 57 | one injured person on one Form 7000-1 |
| `Mines.zip` | 92,060 x 59 | one mine, with its attributes at the snapshot date |
| `MinesProdYearly.zip` | 658,922 x 11 | employee-hours for one mine, calendar year and subunit |

The analytic table has the grain of the accident file (one injured person), with the mine's attributes and its previous-year exposure and case history joined on. MSHA published the three archives on 9 October 2026 and they were pulled on 14 October 2026 at 12:06 UTC. The SHA-256 of every file is pinned in `data/raw/SNAPSHOT.json` and in `mlda.config.SOURCES`, and `mlda-download` refuses a file whose hash differs. MSHA refreshes the files weekly, so the pin is what keeps results comparable. The three archives (66 MB) are committed, so every clone analyses the identical snapshot and needs no network access; the extracted `.txt` files (about 330 MB) are git-ignored and recreated by `mlda-download`.

## Reproduce

Run every command from the repository root. Python 3.12 is required (`requires-python = ">=3.12,<3.13"`). Every stochastic call uses `RANDOM_STATE = 42` (`mlda.config`). The repository already holds the data archives, processed tables, tuned models, metrics and figures of the full run, so the notebook, the app and the tests start without retraining. Commands are identical on Windows (PowerShell) and Unix except where marked.

### Route A: uv (locked, preferred)

```
pip install uv
uv python install 3.12
uv sync --locked --all-groups       # builds .venv from uv.lock and fails if the lock is stale
uv run mlda-download                # extracts the committed archives and verifies each SHA-256
uv run mlda-train                   # optional: full study, rebuilds data/processed, models/, reports/
uv run mlda-train --quick           # optional: two-point grids, 10,000 training rows, 3 folds
uv run jupyter lab notebooks/01_end_to_end.ipynb
uv run streamlit run app/streamlit_app.py
uv run pytest -m "not slow"         # fast suite
uv run pytest                       # also executes the notebook and the quick end-to-end runs
```

Both `mlda-train` modes write into `data/processed`, `models` and `reports`, so a quick run replaces the committed full-run artefacts with smaller-grid results. `git restore data/processed models reports` brings the committed versions back. On Unix and Git Bash, `make sync`, `make test`, `make app` and the other targets in the `Makefile` wrap the same commands.

python3.12 -m venv .venv            # Windows: py -3.12 -m venv .venv

## Method in brief

- **Filters and target.** Accident years 2010 to 2025 and degree-of-injury codes 01 to 06. `lost_time` = 1 for fatality, permanent disability, days away, or days away and restricted activity (codes 01 to 04); 0 for restricted activity only or no days away (05, 06). N = 101,609, prevalence 48.6 %.
- **Joins.** Left joins from the accident rows, each with `validate="many_to_one"` and an asserted row count: Mines on `MINE_ID` (100.0 % matched), mine-year production on `MINE_ID` and the previous calendar year (98.8 %), and counts of earlier cases filed before each accident.
- **Cleaning.** Thirty error rules (E1 to E30) are documented in `docs/data_profile.md`; the 17 implemented in `mlda.cleaning` are logged with row counts in `reports/metrics/error_rules.csv`.
- **Features.** 55 inputs, 552 columns after the default one-hot preprocessor. Columns that encode the outcome (`DAYS_LOST`, `DAYS_RESTRICT`, `RETURN_TO_WORK_DT`, `CLOSED_DOC_NO` and others) are excluded.
- **Split.** `StratifiedGroupKFold` on mine-year groups (32,732 groups), because 82 % of rows share a mine-year with another row. One fold is the 20 % test set (20,320 rows); the 81,289 training rows are cross-validated with five grouped stratified folds. Imputers, scalers, encoders and models are fitted inside scikit-learn Pipelines on training rows only.
- **Models.** Logistic regression, k-nearest neighbours, Gaussian naive Bayes, decision tree, random forest, histogram gradient boosting, RBF support vector machine and multi-layer perceptron. Seven are tuned with `GridSearchCV`; the random forest uses `RandomizedSearchCV`. Four reference rules give the baseline.
- **Thresholds.** Operating thresholds come from out-of-fold training probabilities: specificity 0.40 (the review-capacity assumption), a 50 % flag rate, and the cost-optimal point for cost ratios from 2:1 to 30:1. The test rows only score them.
- **Checks.** A temporal split (tune on 2010 to 2019, score 2020 to 2025: `hist_gb` ROC-AUC 0.834), sensitivity runs (dropping the one pure level `NATURE_INJURY_CD=100` costs 0.003 ROC-AUC; a split grouped by mine gives 0.838), McNemar against the lookup rule (p < 0.001) and a paired fold test of the top two models (corrected p = 0.044).
- **Follow-up checks.** Run after the test scoring, so they are reported as checks and changed no choice: `uv run python -m mlda.followup` writes `reports/metrics/followup_checks.json` and `reports/cv/followup_*_cv_results.csv`. They cover wider grids for KNN, the random forest and `hist_gb` (validation PR-AUC gains of 0.000, 0.001 and 0.002 over the stored searches); logistic regression given the joint nature x body part x sector cell (cross-validated PR-AUC 0.829 against 0.820 without it and 0.838 for `hist_gb`); S5 among the top 50 % of test scores; recall at one equal workload; and the 11,290 test reports still open at filing (ROC-AUC 0.812).

Success criteria, fixed before modelling and evaluated for `hist_gb` on the held-out test rows (`reports/metrics/success_criteria.json`):

| # | Criterion | `hist_gb` | Result |
|---|---|---|---|
| S1 | ROC-AUC >= 0.80 | 0.843 | pass |
| S2 | PR-AUC >= 0.75 | 0.841 | pass |
| S3 | recall >= 0.92 at specificity 0.40 | 0.943 (specificity 0.403) | pass |
| S4 | cost per 1,000 cases below the review-everything floor (102,825) and the lookup rule at 2:1, 3:1, 5:1 | 65,896, 77,697, 87,638 (lookup 73,553, 85,472, 98,061) | pass |
| S5 | recall >= 0.78 at the out-of-fold threshold for a 50 % flag rate (planned as: among the 50 % of cases ranked highest) | 0.775 at a 50.6 % flag rate; 0.769 among the top 50 % of test scores | **fail** |
| S6 | Brier score <= 0.20 | 0.161 | pass |
| S7 | McNemar and paired fold test reported | both reported | pass |

S5 is missed by 0.005. The multi-layer perceptron reaches 0.790 on S5 by flagging 52.5 % of the cases and is the only candidate that passes all seven criteria; among the top 50 % of test scores, the planned form of S5, it reaches 0.768 against 0.769 for `hist_gb`, so neither passes. `hist_gb` stays the final model because the selection rule, cross-validated PR-AUC fixed before any test score was computed, ranks it first (0.838 against 0.833), and the choice was not revised after the test result. At cost ratios of 10:1 and above the model saves little against reviewing every case (4.3 % at 10:1, 0.1 % at 20:1, 0.3 % at 30:1), so its value lies in ranking cases under limited review capacity.

## Tests and CI

`pytest` is configured in `pyproject.toml` (`tests/`, 900-second timeout per test, marker `slow`). The 412 tests cover the loaders and joins (300-row fixtures plus counts on the real data), the schema, each error-correction rule on hand-built rows, IQR and Z-score flags, the feature formulas, leakage guards, every preprocessing option, train-only fitting, the grouped split (disjoint indices, prevalence within 1 percentage point, reproducibility), the model zoo and tuner, metrics against hand-computed confusion matrices, the threshold and cost model, persistence round trips, figure builders, the command-line parsers, the download checksums, the submission packer, the follow-up checks, and a Streamlit `AppTest` run over every page, including a live search with the preprocessing chosen on the Preprocessing page. Tests that need the extracted MSHA files or the committed artefacts skip themselves when these are absent, so run `mlda-download` first.

Seventeen tests carry the `slow` marker: the ten notebook tests (regenerate the notebook, execute it in a temporary copy within 15 minutes, check headings and banned phrases) and seven tests that train models through the quick pipeline. `-m "not slow"` leaves them out (395 tests remain). Lint is `uv run ruff check src tests app report notebooks`.

GitHub Actions (`.github/workflows/ci.yml`; push to `main`, pull requests, Monday 06:00 UTC, manual dispatch) runs five jobs:

1. `test`: Ubuntu and Windows, `uv sync --locked --all-groups`, ruff, `mlda-download`, `pytest -m "not slow"`.
2. `lock-and-exports`: `uv lock --check`, and `requirements.txt` and `app/requirements.txt` must equal fresh exports.
3. `pip-fresh-venv`: Ubuntu and Windows, Python 3.12, plain pip from `requirements.txt`, import check, `pytest -m "not slow" -k "not app_smoke"`.
4. `notebook`: `pytest -m slow` on Ubuntu (not on pull requests).
5. `docker`: image build and health check (not on pull requests).

## Deployment

Primary target: Streamlit Community Cloud.

1. Push this repository to a public GitHub repository. The app reads `data/processed`, `models` and `reports`, so they must be committed.
2. Sign in at https://share.streamlit.io with GitHub and choose "Create app".
3. Pick the repository, the branch `main` and the entrypoint `app/streamlit_app.py`.
4. Under "Advanced settings" select Python 3.12. Cloud ignores `.python-version`.
5. Deploy. Cloud installs from `app/requirements.txt`, the dependency file beside the entrypoint.
6. Copy the URL into the "Deployed at" line above and into `repo_url` and `app_url` in `report/report_meta.json`.

A Cloud app sleeps after about 12 hours without a visit, so open it shortly before marking. Fallback: a Render free web service reads `uv.lock` and `.python-version`; the start command is `streamlit run app/streamlit_app.py --server.port $PORT --server.address 0.0.0.0`. Locally, `uv run streamlit run app/streamlit_app.py` or the Docker route serves the same app at http://localhost:8501.
