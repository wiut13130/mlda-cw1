# Predicting lost-time mine injuries from MSHA open data

Module 6COSC017C Machine Learning and Data Analytics, Coursework 1, student ID 13130. The business question: when a mine operator files an injury on US Form 7000-1, can the case be flagged as a likely lost-time injury on receipt of the form, so that the insurer or self-insured operator opens the reserve, the return-to-work plan and medical case management earlier? The data are three open files from the US Mine Safety and Health Administration (MSHA), joined into one table of 101,609 injured persons from 2010 to 2025, of whom 48.6 % had a lost-time outcome. The final model is a histogram gradient boosting classifier (`hist_gb`), ranked first by cross-validated PR-AUC. On the 20,320 held-out rows it reaches ROC-AUC 0.843 and PR-AUC 0.842 (`reports/metrics/comparison.csv`). Two operating points are kept apart. The capacity threshold, 0.211, is chosen on out-of-fold probabilities for specificity 0.40 on all training rows; on all test filings it flags 76.3 % of reports, with recall 0.941, specificity 0.406 and precision 0.600 (`reports/metrics/comparison_operating_point.csv`). The workload rule, which is the recommendation, reviews the top three in four of the reports still open at filing by score (see "Method in brief"). The lookup baseline, the lost-time rate of each nature of injury x body part x sector cell on the training rows, reaches ROC-AUC 0.804.

## Data

Three files from MSHA Open Government Data (https://arlweb.msha.gov/OpenGovernmentData/OGIMSHA.asp):

| File | Rows x columns | One row is |
|---|---|---|
| `Accidents.zip` | 275,220 x 57 | one injured person on one Form 7000-1 |
| `Mines.zip` | 92,060 x 59 | one mine, with its attributes at the snapshot date |
| `MinesProdYearly.zip` | 658,922 x 11 | employee-hours for one mine, calendar year and subunit |

The analytic table has the grain of the accident file (one injured person), with the mine's attributes and its previous-year exposure and case history joined on. MSHA published the three archives on 9 October 2026 and they were pulled on 14 October 2026 at 12:06 UTC. The SHA-256 of every file is pinned in `data/raw/SNAPSHOT.json` and in `mlda.config.SOURCES`, and `mlda-download` refuses a file whose hash differs. MSHA refreshes the files weekly, so the pin is what keeps results comparable. The three archives (66 MB) are committed, so every clone analyses the identical snapshot and needs no network access; the extracted `.txt` files (about 330 MB) are git-ignored and recreated by `mlda-download`.

## Reproduce

Run every command from the repository root. Python 3.12 is required (`requires-python = ">=3.12,<3.13"`). Every stochastic call uses `RANDOM_STATE = 42` (`mlda.config`). The repository already holds the data archives, processed tables, tuned models, metrics and figures of the full run, so the notebook, the app and the tests start without retraining. Commands are identical on Windows (PowerShell) and Unix except where marked.

### Route A: uv (locked, preferred)

```
pip install uv
uv python install 3.12
uv sync --locked --all-groups       # builds .venv from uv.lock and fails if the lock is stale
uv run mlda-download                # extracts the committed archives and verifies each SHA-256
uv run mlda-train                   # optional: full study, rebuilds data/processed, models/, reports/
uv run mlda-train --quick           # optional: two-point grids, 10,000 training rows, 3 folds
uv run jupyter lab notebooks/01_end_to_end.ipynb
uv run streamlit run app/streamlit_app.py
uv run pytest -m "not slow"         # fast suite
uv run pytest                       # also executes the notebook and the quick end-to-end runs
```

Both `mlda-train` modes write into `data/processed`, `models` and `reports`, so a quick run replaces the committed full-run artefacts with smaller-grid results. `git restore data/processed models reports` brings the committed versions back. On Unix and Git Bash, `make sync`, `make test`, `make app` and the other targets in the `Makefile` wrap the same commands.

## Method in brief

- **Prediction moment and cohort.** The score is computed on receipt of Form 7000-1, at its filing date (a median of 8 days after the accident), from the fields the form and the mine records carry at that date. At filing 45.0 % of in-scope reports already carry a return-to-work date and are not scored; the operational cohort is the 55 % still open at filing (11,290 of the 20,320 test reports, 71.2 % of them lost-time). The extract holds only the final degree code, so it cannot show what the filer knew at filing: the study is retrospective, and a prospective trial is needed before the score is relied on.
- **Operating points and the workload rule.** The capacity threshold (0.211) is the lowest out-of-fold threshold with specificity 0.40 on all training rows. It flags 76.3 % of all test filings but would flag 90.0 % of the open reports, more than a review capacity of three in four, so the recommendation is the workload rule: review the top three in four of open-at-filing reports by score. The deployed cut-off, 0.376, is the 25th percentile of the out-of-fold scores of the open training reports, so no test row enters it; on the 11,290 open test reports it flags 74.3 % and finds 0.850 of the lost-time cases. At exactly the top 75 % of open reports by test score, recall is 0.855 and precision 0.812, level with the MLP (0.855) and above the lookup baseline (0.828) and random selection (0.75). The probabilities are calibrated to all filings and run 0.12 below the observed rate on open reports (mean predicted 0.592 against 0.712); the rule uses the ranking only. A paired mine-year bootstrap puts HGB 0.027 ahead of the lookup baseline in recall under the rule (95 % interval 0.021 to 0.033) and level with the MLP (0.000, interval -0.003 to 0.004). An HGB fitted on open-at-filing training rows alone reaches recall 0.877 under the rule, so a prospective trial should fit on open reports.
- **Filters and target.** Accident years 2010 to 2025 and degree-of-injury codes 01 to 06. `lost_time` = 1 for fatality, permanent disability, days away, or days away and restricted activity (codes 01 to 04); 0 for restricted activity only or no days away (05, 06). N = 101,609, prevalence 48.6 %.
- **Joins.** Left joins from the accident rows, each with `validate="many_to_one"` and an asserted row count: Mines on `MINE_ID` (100.0 % matched), mine-year production on `MINE_ID` and the previous calendar year (98.8 %), and counts of earlier cases filed before each accident.
- **Cleaning.** Thirty error rules (E1 to E30) are documented in `docs/data_profile.md`; the 17 implemented in `mlda.cleaning` are logged with row counts in `reports/metrics/error_rules.csv`.
- **Features.** 52 inputs, 546 columns after the default one-hot preprocessor. The three Mines-snapshot flags (safety committee, Part 48 training, portable operation) are not inputs, because their value at the time of each accident cannot be established from a snapshot of the Mines file; the location and commodity fields stay, and the Section 103(i) status is dated to the accident (`status_103i_at_accident`). Columns that encode the outcome (`DAYS_LOST`, `DAYS_RESTRICT`, `RETURN_TO_WORK_DT`, `CLOSED_DOC_NO` and others) are excluded.
- **Split.** `StratifiedGroupKFold` on mine-year groups (32,732 groups), because 82 % of rows share a mine-year with another row. One fold is the 20 % test set (20,320 rows); the 81,289 training rows are cross-validated with five grouped stratified folds. Imputers, scalers, encoders and models are fitted inside scikit-learn Pipelines on training rows only.
- **Models.** Logistic regression, k-nearest neighbours, Gaussian naive Bayes, decision tree, random forest, histogram gradient boosting, RBF support vector machine and multi-layer perceptron. Seven are tuned with `GridSearchCV`; the random forest uses `RandomizedSearchCV`. Four reference rules give the baseline.
- **Thresholds.** Operating thresholds come from out-of-fold training probabilities: specificity 0.40 on all training rows (the review-capacity assumption), a 50 % flag rate, and the cost-optimal point for cost ratios from 2:1 to 30:1. The workload rule's cut-off comes from the out-of-fold scores of the open training reports. The test rows only score them.
- **Checks.** A temporal split (tune on 2010 to 2019, score 2020 to 2025: `hist_gb` ROC-AUC 0.834), sensitivity runs (dropping the one pure level `NATURE_INJURY_CD=100` costs 0.003 ROC-AUC; a split grouped by mine gives 0.838), McNemar against the lookup rule (p < 0.001) and a paired fold test of the top two models (corrected p = 0.029). Five altered-input refits of `hist_gb` with the stored hyper-parameters (`without_immed_reportable`, `without_status_103i`, `resolved_lag_counts`, `exposure_blank_if_q4_incomplete` and `history_without_test_outcomes`) move test PR-AUC by between -0.002 and +0.001. The last is a history audit: 14.1 % of the training rows (11,426; 11,416 of them with a non-blank history) carry a previous-year case history drawn from a mine-year that is in the test split, and refitting with that history set to missing changes test PR-AUC by less than 0.001 (+0.0006). The temporal split has no such overlap, because every training row precedes every test row.
- **Follow-up checks.** Run after the test scoring, so they are reported as checks and changed no choice: `uv run python -m mlda.followup` writes `reports/metrics/followup_checks.json`, the three tables `followup_capacity_policy.csv`, `followup_workload_rule.csv` and `followup_open_calibration.csv` in `reports/metrics`, and `reports/cv/followup_*_cv_results.csv`. They cover wider grids for KNN, the random forest and `hist_gb` (validation PR-AUC gains of 0.000, 0.001 and 0.002 over the stored searches); logistic regression given the joint nature x body part x sector cell (cross-validated PR-AUC 0.829 against 0.820 without it and 0.838 for `hist_gb`); S5 among the top 50 % of test scores; recall at one equal workload; the capacity threshold and the exact top 50 % and top 75 % compared across HGB, the MLP, the lookup baseline and the hand rule, on all test rows and on the 11,290 reports still open at filing (ROC-AUC 0.812); the workload rule's cut-off and its test result; calibration on the open reports; the paired mine-year bootstrap of the comparison; and the refit on open-at-filing training rows alone.

Success criteria, fixed before modelling and evaluated for `hist_gb` on the held-out test rows (`reports/metrics/success_criteria.json`):

| # | Criterion | `hist_gb` | Result |
|---|---|---|---|
| S1 | ROC-AUC >= 0.80 | 0.843 | pass |
| S2 | PR-AUC >= 0.75 | 0.842 | pass |
| S3 | recall >= 0.92 at specificity 0.40 | 0.941 (specificity 0.406) | pass |
| S4 | cost per 1,000 cases below the review-everything floor (102,825) and the lookup rule at 2:1, 3:1, 5:1 | 65,817, 76,781, 87,205 (lookup 73,553, 85,472, 98,061) | pass |
| S5 | recall >= 0.78 at the out-of-fold threshold for a 50 % flag rate (planned as: among the 50 % of cases ranked highest) | 0.777 at a 50.7 % flag rate; 0.770 among the top 50 % of test scores | **fail** |
| S6 | Brier score <= 0.20 | 0.161 | pass |
| S7 | McNemar and paired fold test reported | both reported | pass |

S5 is missed by 0.003. The multi-layer perceptron misses it as well, with 0.777 at a 51.1 % flag rate and 0.769 among the top 50 % of test scores (the planned form of S5) against 0.770 for `hist_gb`, so no candidate passes all seven criteria. `hist_gb` stays the final model because the selection rule, cross-validated PR-AUC fixed before any test score was computed, ranks it first (0.838 against 0.831), and the choice was not revised after the test result. S3 was set for all filings and is met at the capacity threshold; under the workload rule recall on open reports is 0.850 (0.855 at exactly the top 75 % by test score), below that target. At cost ratios of 10:1 and above the model saves little against reviewing every case (4.6 % at 10:1), and at 20:1 and 30:1 its cost-optimal threshold costs 0.5 % and 0.3 % more than reviewing every case on the test rows, so its value lies in ranking cases under limited review capacity.

## Tests and CI

`pytest` is configured in `pyproject.toml` (`tests/`, 900-second timeout per test, marker `slow`). The 485 tests cover the loaders and joins (300-row fixtures plus counts on the real data), the schema, each error-correction rule on hand-built rows, IQR and Z-score flags, the feature formulas, leakage guards, every preprocessing option, train-only fitting, the grouped split (disjoint indices, prevalence within 1 percentage point, reproducibility), the model zoo and tuner, metrics against hand-computed confusion matrices, the threshold and cost model, persistence round trips, figure builders, the command-line parsers, the download checksums, the submission packer (zip contents, the commit history, a bundle that clones, the forbidden-string scan of the history), the follow-up checks (the workload rule's cut-off, the open-cohort calibration bins, the paired bootstrap and the open-only refit, each on hand-built frames), and a Streamlit `AppTest` run over every page, including the `MINE_ID` validation of the inference page and a live search with the preprocessing chosen on the Preprocessing page and the caps of low-memory mode. Tests that need the extracted MSHA files or the committed artefacts skip themselves when these are absent, so run `mlda-download` first.

Seventeen tests carry the `slow` marker: the ten notebook tests (regenerate the notebook, execute it in a temporary copy within 15 minutes, check headings and banned phrases) and seven tests that train models through the quick pipeline. `-m "not slow"` leaves them out (468 tests remain). Lint is `uv run ruff check src tests app report notebooks`.

GitHub Actions (`.github/workflows/ci.yml`; push to `main`, pull requests, Monday 06:00 UTC, manual dispatch) runs five jobs:

1. `test`: Ubuntu and Windows, `uv sync --locked --all-groups`, ruff, `mlda-download`, `pytest -m "not slow"`.
2. `lock-and-exports`: `uv lock --check`, and `requirements.txt` and `app/requirements.txt` must equal fresh exports.
3. `pip-fresh-venv`: Ubuntu and Windows, Python 3.12, plain pip from `requirements.txt`, import check, `pytest -m "not slow" -k "not app_smoke"`.
4. `notebook`: `pytest -m slow` on Ubuntu (not on pull requests).
5. `docker`: image build and health check (not on pull requests).

The workflow runs on GitHub Actions on every push to `main`, on a weekly schedule and on demand; the Actions tab of the repository shows every run. Run the same checks by hand before a push: `uv run ruff check src tests app report notebooks` and `uv run pytest -m "not slow"`.
